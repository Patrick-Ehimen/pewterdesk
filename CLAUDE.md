# pewterdesk

Non-custodial, multi-venue crypto derivatives trading terminal (desktop-first,
web later). No backend - talks directly to exchange APIs from the user's own
machine. Launch venues: Hyperliquid and Aster - both on-chain.
Venue adapters, signing and key handling are Rust; the UI is TypeScript/React
(see `docs/adr/0001-venues-in-rust.md`).

## Architecture rule (read this before touching crates/ or packages/)

`crates/core` (`pewterdesk-core`) defines the cross-cutting contracts, and
nothing else may:

- `ExchangeAdapter` plus the domain types (`Order`, `Position`, `Market`,
  `OrderBook`, ...). Every venue crate (`crates/exchange-<venue>`) implements
  that trait and depends on `core` - never the other way around.
- `KeySource` - how an adapter gets a key, independent of where it's stored.

`KeySource` runs the same direction: `core` owns the trait, the app owns the
implementation (the desktop app backs it with the OS keychain). Venue crates
receive a `KeySource`, they never construct one.

The domain types' TypeScript copies are generated by ts-rs into
`packages/core/src/generated/` (`make rust-bindings`). Never edit them by
hand; change the Rust and regenerate. Their serde attributes are the IPC wire
format, so renaming a field is a breaking change for the frontend.

`packages/ui` and the two `apps/*` depend on `packages/core` for types and
reach venues only through Tauri commands - never a venue crate or a venue's
API directly. That's what makes adding a venue a new crate, not a rewrite of
the UI. `packages/core` also holds `SecretStore` (write, check, delete - no
read), implemented over the keychain in
`apps/desktop/src/secrets/tauriSecretStore.ts`; `apps/web` has no
implementation and is not meant to get one. Onboarding doesn't use it: it goes
through `connect_wallet` (`apps/desktop/src-tauri/src/wallet.rs`), which checks
a key before storing it.

## Layout

- `crates/core` - domain types, the `ExchangeAdapter` trait, `KeySource`,
  and how accounts and their keychain entries are named (`accounts`)
- `crates/engine` - the router and the trading gate (live-trading switch,
  trading rules); the only caller of an adapter's trading methods
- `crates/store` - the engine's event log (SQLite), and each algo's state
- `crates/sim` - `SimVenue`, an adapter fed order books, for testing algos
- `crates/protocol` - what a client may ask the engine (JSON-RPC 2.0,
  versioned), the command language in Rust (`command.rs`, checked against
  `tests/fixtures/commands.json` with the TS parser) and what a line comes
  to (`action.rs`), and where things live on this machine (`local.rs`)
- `crates/link` - `pd`'s and the app's connection to `pdd`, and the
  LaunchAgent that keeps it running
- `crates/calendar` - the economic calendar (and its text helpers), shared
  by the app and `pdd`
- `apps/daemon` (`pdd`) - the engine headless, served over a Unix socket and
  a 127.0.0.1 WebSocket to paired clients
- `apps/cli` (`pd`) - the command line
- `crates/keychain` - the OS keychain bridge and `KeychainKeySource`
- `crates/exchange-hyperliquid`, `-aster`, `-bybit` - one adapter per venue
- `packages/core` - the generated TS domain types and the `SecretStore` contract
- `packages/ui` - shared React components (order ticket, position table, chart wrapper, hotkeys)
- `apps/desktop` - the shipped app: Tauri (Rust shell, keychain, the Tauri commands the UI calls) and this workspace's React frontend
- `apps/web` - the landing site for now: four static pages (home, Features,
  Security, Download) after the editorial mockup in `design/landing/`, one
  `index.html` each, all loading `src/main.tsx`. Copy and facts are in
  `src/content/` (English only), colors from the light palette's tokens. Its
  Security page restates the rules below, so a change to the signing surface
  or key handling may mean a change there. The web build of the terminal is still
  v2, deferred: same frontend stack, but it can't run the Rust adapters as-is
  (needs a WASM build or its own implementation, a browser-wallet signer, and
  a proxy for CORS)

The root `Cargo.toml` is a workspace over `crates/*`, `apps/daemon`, `apps/cli`
and `apps/desktop/src-tauri`;
build output goes to the root `target/`.

## Commands

Run `make` on its own for the full menu. The Makefile is a thin wrapper over
pnpm and cargo, so it can't drift from the underlying scripts.

- `make install` - resolve the workspace and enable the git hooks
- `make check` - what CI runs, in CI's order: lint, typecheck, test, build
- `make check-all` - `check` plus the Rust side, which CI does not cover yet;
  also fails if the generated TS types are stale
- `make rust-bindings` - regenerate `packages/core/src/generated/` after changing `crates/core`
- `make dev` - run the desktop app in a native window (needs Rust)
- `make daemon` - build `pd` and `pdd` (release), signed with the dev
  certificate; then `target/release/pd daemon install` and `pd pair`
- `make dev-cert` - macOS, once per machine: a local self-signed "PewterDesk
  Dev" certificate that `make dev` signs the app with (`scripts/dev-run.sh`),
  so keychain "Always Allow" survives rebuilds instead of prompting each time
- `make dev-ui` - desktop frontend in a browser only, no Rust
- `cargo test -p pewterdesk-keychain -- --ignored` - the keychain tests that
  touch the real OS store, skipped by default
- `make rust-live` - read-only tests against Hyperliquid and Aster mainnet
  (needs the network, no key), one at a time so they stay inside rate limits

Packages are consumed from source: every `package.json` points `main`/`types`
at `./src/index.ts`, and the tsconfigs deliberately carry no `references`.
Don't add them back. Project references redirect module resolution to
`packages/*/dist`, which `tsc --noEmit` then requires to already exist - and
both CI and `make check` typecheck before they build, so it fails on any clean
checkout the moment one package actually imports another. `dist/` is build
output; nothing imports it.

## Security-sensitive code - extra care here

Any change to the code below needs review against
`.claude/commands/security-review.md`, and an explicit callout in the PR
description under a "Security-relevant changes" heading - don't leave a reviewer to
discover it on their own. The reasoning behind the rules is in
`docs/adr/0001-venues-in-rust.md`.

- `crates/keychain` (with the app's commands over it in
  `apps/desktop/src-tauri/src/keychain.rs`) - the OS keychain bridge, and the
  only place key material is stored. Keys never touch disk, env vars, or logs.
  Note that keyring's `BadEncoding` and `Ambiguous` error variants carry
  credential material, which is why keyring errors are mapped by hand rather
  than formatted into a string. Nothing reads a key back to JS: Rust reads it
  through `KeychainKeySource`, the app's `KeySource`. Whether a key is stored
  (`has_secret`, and the AI page's and news wire's key status) is a search by
  service and account that loads attributes only, never the secret, so on
  macOS it asks for no password (a store that can't search that way falls
  back to reading and dropping it). On macOS a build this
  Mac hasn't run (named by its Mach-O UUID: an install, an update, a
  rebuild) first shows a note that macOS will ask for the password
  (`keychain_notice.rs`, `components/KeychainNotice.tsx`); until it's
  dismissed, nothing at start reads the keychain - the app doesn't mount,
  the tray panel and floating window wait, and so do the algos' reconciler
  and the daemon link (those two for 2 minutes at most).
- `apps/desktop/src-tauri/src/wallet.rs` and `crates/exchange-hyperliquid/src/agent.rs`
  - onboarding. The pasted key crosses IPC once, into `connect_wallet`, which
  wraps it in `Zeroizing`, refuses the main wallet's own key, and stores it
  only if the venue lists it as an approved agent of that account. The
  commands return public addresses only.
- `crates/exchange-aster/src/agent.rs` (with `wallet.rs`) - Aster
  onboarding and request signing. Aster has no API key: an API wallet
  (agent) the main wallet approves signs every private request. Rust
  generates the agent key and builds the approval, whose permissions are
  fixed in the code - perpetuals only, no spot, no withdrawals - so nothing
  from the UI can widen them. After Aster accepts it, Rust asks Aster what
  the agent may do and stores the key only if it can't withdraw
  (`check_trade_only`, which also treats a missing answer as "can"). A
  pasted key isn't taken for Aster. Requests are signed over exactly the
  parameter string sent (EIP-712, `Message(string msg)`), with a fresh
  microsecond nonce; the key is held only for that call. Checked against
  `eth_account` vectors and Aster's live API.
- `apps/desktop/src-tauri/src/bybit_key.rs` and `crates/exchange-bybit/src/auth.rs`
  - Bybit onboarding. The API key and secret cross IPC once, into
  `connect_bybit_key`, which signs one fixed request (`/v5/user/query-api`)
  to ask Bybit what the key may do, and stores a live key only if every
  permission is on `auth::ALLOWED` (contract trading, nothing that moves
  funds) - an allowlist, so anything unknown is refused. Demo Trading keys
  skip the allowlist (demo funds only); they're still checked on the demo
  host, where live keys don't authenticate. The commands return the UID and
  permissions only.
- `apps/desktop/src-tauri/src/browser_connect.rs` - connecting a browser
  extension wallet. It serves a one-time page on 127.0.0.1 (random port, a
  random token in every path, the exact Host checked, posts only from the
  page's own origin) that asks the extension to sign the approval
  `wallet.rs` builds, for the venue the app named when it started the page
  (the page can't choose). It stops after a connection, a cancel, or 10
  minutes.
- `apps/desktop/src-tauri/src/coin_info.rs` - the Markets panel's Overview
  tab, from CoinGecko (`api.coingecko.com` only), and a coin's logo as a last
  resort when no venue has one (`coin_logo`; the image from
  `coin-images.coingecko.com` only, a raster image within a size cap, never
  for a stock, ETF, commodity or forex market), and the Maps page's market
  heatmap (`coin_markets`: the largest coins of one of a fixed set of
  sectors - the UI names the sector, Rust maps it to CoinGecko's category
  and builds the request, spaced and cached). Its optional demo API key
  lives in the keychain (`coingecko:demo`) and is never returned. Coin links
  reach JS as labels and indexes and open only via `open_coin_link`, which
  opens a URL Rust itself fetched, filtered by `safe_url` (it goes through
  the OS shell on Windows) - never a URL from the UI.
- `apps/desktop/src-tauri/src/okx_liquidations.rs` - OKX's public
  liquidation history, for the Maps page. OKX is a data source here, not a
  venue: no key, nothing signed, two read-only GETs on `www.okx.com` only
  (no redirects followed). The UI names a market only from the list the
  module itself returned; anything else is refused before a request is built.
- `apps/desktop/src-tauri/src/news_feeds.rs` - news sites' RSS feeds, for
  the News page. Publishers are data sources, not venues: no key, nothing
  signed, one read-only GET each to a fixed list of hosts (`PUBLISHERS`; no
  redirects followed, a size cap). Feed text reaches the UI as plain text
  (markup stripped, lengths bounded), never a link: an article opens only
  via `open_news_article`, by an id, as a URL Rust itself fetched - https,
  on its publisher's own host, its query string dropped, filtered by
  `safe_url`. Adding a publisher is a security-relevant change.
- `apps/desktop/src-tauri/src/econ_calendar.rs` - the week's economic
  calendar, for the Calendar panel, from Forex Factory's public export. A
  data source, not a venue: no key, nothing signed, one read-only GET to one
  fixed URL (`FEED`, on `nfs.faireconomy.media`; no redirects followed, a
  size cap), kept an hour. It reaches the UI as text only (every field
  through `plain`, bounded), with no links. Changing the source is a
  security-relevant change.
- `apps/desktop/src-tauri/src/news_wire.rs` - the live news wire, for the
  News feed panel: posts from X and headlines from two aggregators, Tree
  News (Tree of Alpha) and Phoenix News, over their websockets. Data
  sources, not venues: nothing signed, nothing sent but the login, three
  fixed addresses (`TREE_WS`, `TREE_HISTORY`, `PHOENIX_WS`; no redirects,
  message and size caps). Tree works keyless, about 5 seconds behind;
  Phoenix needs a key. Their keys live in the keychain (`treenews:api`,
  `phoenix:api`), each sent only to its own source in the login message,
  never returned (`news_keys` says only whether one is stored). Items reach
  the UI as bounded text, tickers checked. A link stays in Rust and opens
  only via `open_wire_link`, by id: https on any host (news links anywhere,
  so the page shows the host first), filtered by `safe_url`. Adding a
  source, or letting a link or a ticker do more than open or show, is a
  security-relevant change.
- `apps/desktop/src-tauri/src/ai_assistant.rs` and `ai_providers.rs` -
  PewterDesk AI, the analyst behind the AI page, on the trader's pick of
  model (a fixed list per provider, `Provider::models`): Anthropic's Claude
  (Messages API, `api.anthropic.com/v1/messages`), Google's Gemini
  (Interactions API, `generativelanguage.googleapis.com/v1beta/interactions`,
  `store: false`) or OpenAI's ChatGPT models (Responses API,
  `api.openai.com/v1/responses`, `store: false`). Reached from Rust only,
  each at its one fixed address (no redirects followed), with the trader's
  own key for it, kept in the keychain (`anthropic:api`, `gemini:api`,
  `openai:api`), sent only to its own provider and never returned
  (`ai_key_status` says only which are stored). A chat stays with the
  provider it began on: its transcript is that provider's own.
  Not a venue and not on the signing surface: its tools are read-only
  market data through the adapters (`get_candles`, `get_order_book`,
  `get_funding_history`, `get_open_interest`, `get_long_short_ratio`,
  `get_recent_trades` - the trades stream's first snapshot - and
  `find_markets`; each takes a `venue`, so it can compare venues), OKX's
  public liquidation history (`get_liquidations`, through
  `okx_liquidations::liquidations`), what the app's own data sources already read, each
  through its own module and fixed hosts (`search_x_posts` over the news
  wire's X posts - Tree's recent items plus what the live wire brought in,
  `news_wire::recent_items`; `search_headlines` over the wire's headlines,
  the RSS feeds and Bybit's announcements; `get_economic_calendar`),
  Anthropic's own web search, and
  `mark_chart`, whose analysis comes back to the page only as numbers,
  candle times and bounded labels to draw (`analysis` on `OpenAlgoChart`:
  the chart's own drawings - supply/demand zones as rectangles, Fibonacci
  retracements, trend lines, levels as rays - pinned to the candles,
  read-only and never saved; `analysisDrawings` in `lib/openAlgoChart.ts`). No tool reaches the router, an account or a key, or
  takes a URL or host. The trader's own account (`get_account`,
  `get_fills`, `get_closed_trades`: the adapters' read-only account, fills
  and closed-trade reads, for the account the page has connected on each
  venue) is read only with account access on - a switch kept and enforced
  in Rust (`ai-account-access.json` in the data folder, `set_ai_account_access`),
  off by default, turned on only from the AI page's side panel, which says
  that what it reads goes to the model's provider. The tools are always
  declared (a conversation's tools can't change) and refuse while it's off.
  Posts and headlines are other people's text, given
  to the model as data (the prompt says never to follow them). Answers reach the page as bounded text, drawn as
  text (`lib/aiText.ts`: no markup, no links). The conversation is the
  API's transcript, kept with the chats in `ai-chats.json` in the app's
  data folder (written whole by `save_ai_chats`, 0600; never key material)
  and handed back whole; Rust only appends to it. Adding a provider, or
  sending a request anywhere else, is a security-relevant change. Giving the analyst a tool that trades, reads an
  account, or opens a link, or sending its requests anywhere else, is a
  security-relevant change.
- Signing code in each `crates/exchange-<venue>` - what turns a key into a
  signed venue action. The highest-stakes code in the repo. Hold keys only as
  `Zeroizing` and only for the signing call. Bybit's:
  `crates/exchange-bybit/src/orders.rs` builds the create/cancel bodies (every
  field a constant or checked against the live market's tick and step; market
  orders always go as IOC limits at the slippage bound), and `auth.rs` signs
  (HMAC over exactly the bytes sent). Demo accounts (ids `demo:{uid}`, keys
  under `bybit:demo:{uid}`) use Bybit's demo host, `api-demo.bybit.com`.
  Coin logos come from Bybit's convert coin list (`icons.rs`): one more
  signed, read-only request (`/v5/asset/exchange/query-coin-list`, only the
  logos are read), and the images from Bybit's image host, `t1.bycsi.com` -
  a listed logo anywhere else is ignored.
- Hyperliquid's and Aster's order signing.
  `crates/exchange-hyperliquid/src/orders.rs` builds the `order` and
  `cancel` actions (the asset number from the venue's own list, size and
  prices checked against Hyperliquid's rules, a take-profit and stop-loss
  as reduce-only orders grouped with the entry), `batchModify` (a resting
  limit order's price and size; everything else about it read back from
  the venue and kept), `updateLeverage` (leverage and margin mode) and a
  position's exits (reduce-only trigger orders closing all of it; the new
  one placed before the old is cancelled), and `agent.rs` signs them
  with the API wallet (`sign_action`: EIP-712 over the action's msgpack
  hash, a fresh millisecond nonce; it takes `orders.rs`'s own type, not
  bytes). Checked against the official Python SDK's signing vectors.
  It also builds a venue-run TWAP (`twapOrder`, 5 minutes to 7 days, the
  size checked; its id kept as `twap:<id>`, cancelled with `twapCancel`)
  and the dead-man's switch (`scheduleCancel`, which can only cancel every
  open order of the account at a set time). Every action is signed with an
  expiry, `expiresAfter` (60 seconds), so one held up can't execute late.
  Those three were checked against the SDK's own `sign_l1_action`
  (`scheduleCancel` against its published vectors).
  `crates/exchange-aster/src/orders.rs` builds the parameters of
  `POST`/`DELETE`/`PUT /fapi/v3/order` (`PUT` changes a limit order's price
  and size only), `/fapi/v3/leverage`, `/fapi/v3/marginType`, and a
  position's exits (`closePosition` stop and take-profit at market, on the
  mark), and the dead-man's switch (`/fapi/v3/countdownCancelAll`, per
  market, 10 seconds to an hour; `0` stops it), signed by
  `agent::sign_request` and sent exactly as signed.
  Neither venue gets a trailing stop: Hyperliquid has none, and Aster's
  moves by a percentage rather than the distance asked for, so it's
  refused, not approximated. Neither crate has a request that withdraws,
  transfers or approves a key, and the API wallet's key is never used in
  the domain those are signed in.
- The `ExchangeAdapter` trait, the engine's router that calls it
  (`crates/engine/src/router.rs`, `Engine`), and the Tauri commands that
  wrap the router (`place_order`, `cancel_order`, `amend_order`,
  `set_position_protection`, `set_leverage`, `set_margin_mode` in
  `venues.rs`). Together they are the entire signing surface: place, cancel and amend orders (an open order's
  price, size or attached TP/SL - never its market, side or kind; placing
  includes a venue-run TWAP, `OrderKind::Twap`, on Hyperliquid only, and
  cancelling includes the venue's dead-man's switch, `schedule_cancel`,
  which only the engine arms - no Tauri command), set a
  position's take-profit, stop-loss and trailing stop (protective,
  reduce-only, closing the whole position), and set the leverage (1 to the
  market's maximum) and margin mode (cross or isolated; account-wide on
  Bybit) - nothing else. Never add withdraw,
  transfer, key approval, or anything that signs caller-supplied bytes or
  typed data. The router builds the account's keychain reference itself
  (`trading_account`, from `core::accounts`) and is the only caller of an
  adapter's trading methods. It logs every command with its origin (`Origin`,
  where in the app it came from - a label that grants nothing; the frontend
  passes it with each trading command), the gate's decision and the venue's
  answer, and gives every order a client order id of its own (`0x` + the
  log's engine id + the command's sequence number), written to the log
  before the order is sent. An opening order whose id can't be logged is
  refused (`Blocked("unrecorded")`); reduce-only orders, cancels and the
  rest still go through: a Bybit demo account trades as soon as it's
  connected, every live account (Bybit, Hyperliquid, Aster) only once live
  trading is turned on for it. Every venue implements all six, but for a
  trailing stop on Hyperliquid and Aster.
- `crates/engine/src/algo/` (its commands in
  `apps/desktop/src-tauri/src/algos.rs`) - algo orders: a chaser, a TWAP
  (on this machine, or the venue's own on Hyperliquid), a scaled ladder.
  Every order an algo sends goes through the router (`Origin::Algo`, the
  algo's id on the command), so the switch, the rules, the log and client
  ids apply as to the ticket; a refusal pauses it, it never retries around
  one. An order whose answer was lost is looked up by client id, never
  resent. Stale market data or a lost account feed pauses it; after a
  reconnect it re-reads its orders first. A per-venue request budget
  (`budget.rs`) keeps it under the venue's limits. Session only: when the
  app closes it stops, and the next start's reconciler marks it stopped
  and cancels what of it still rests (a venue-run TWAP is followed again).
  While one runs on this machine the engine keeps the venue's dead-man's
  switch armed (`heartbeat.rs`: every 30 seconds, a 2-minute countdown;
  on Hyperliquid it would cancel every open order of the account, on
  Aster that market's; Bybit has none we can use). `halt` stops every algo
  and cancels what they placed. Giving algos a way to the venue that skips
  the router is a security-relevant change.
- `apps/daemon` (`pdd`), `crates/protocol`, `crates/link` and `apps/cli`
  (`pd`) - the daemon and its clients ("always on"). `pdd` runs the same
  engine as the app - router, gate, log, client ids, algos - and serves it
  only on this machine: a Unix socket (0600, the umask narrowed around the
  bind) for `pd`, and a WebSocket on 127.0.0.1 for the app that refuses any
  request with an `Origin` (a browser) or a `Host` but its own (DNS
  rebinding). Only paired clients get past `hello`: pairing is approved by
  the person at the machine (`pdd`'s terminal, or a macOS dialog showing
  the code the client shows; the client's name goes to it as an argument,
  never into the script), never over the protocol; the client keeps its
  token in its keychain (`pd:token`, `app:pdd-token`), `pdd` only a SHA-256
  of it (`pdd-clients.json`, 0600), compared in constant time; revoking
  takes effect on the next call. The protocol (`rpc.rs`) is the six
  trading operations, read-only queries, algo control, `halt`, `flatten`
  (reduce-only market orders through the router) and pairing - nothing
  that signs, withdraws, transfers or carries key material. `pd`'s
  commands are logged with the origin `pd` whatever it says. A panic aborts
  `pdd` (launchd restarts it; it reconciles first). With "always on" set
  (Settings, `src-tauri/src/daemon.rs`, `always-on.json`) the app's six
  trading commands and its algo commands go to `pdd`, and are refused - not
  sent from the app's own engine - while it can't be reached; cancels
  always go through. The app's engine and `pdd`'s share the gate files
  (`crates/engine/src/kept.rs`: each re-reads one the other changed, and
  writes it whole) and take one lock per account (`owner.rs`, `flock` in
  the data folder's `locks`): an account another engine holds is refused
  (`Blocked("another-engine")`), and its algos are left to that engine at
  start; one that died let its lock go, so its algos are taken up.
  Adding a protocol method, a listener, or a way to pair is a
  security-relevant change.
- `crates/store` - the event log (`events.sqlite3` in the app's data
  folder; SQLite, WAL, append-only): every routed command, gate decision,
  client order id and venue result. Never key material - not a key, a
  signature, a signed payload or a keychain reference.
- `crates/engine/src/live.rs` (its commands in
  `apps/desktop/src-tauri/src/live_trading.rs`) - the per-account switch for
  live trading, kept and enforced in Rust (Bybit UIDs, and Hyperliquid and
  Aster accounts as `<venue>:<address>`, in `live-trading.json` in the app's
  config folder; no key material). Off by default. Turning it on asks the
  venue again what the stored key may do and refuses anything but that
  account's own trade-only key (on Hyperliquid and Aster: the API wallet
  still approved for it - `wallet::verify_trade_only`), failing closed
  (offline included); disconnecting a key turns it off. There is no order
  size cap. It guards against a live order sent by mistake, not against
  the page itself. Opening trading to another venue, or loosening this
  switch, is a security-relevant change.
- `crates/engine/src/rules.rs` (its commands in
  `apps/desktop/src-tauri/src/trading_rules.rs`) - the trader's own rules
  (daily loss, drawdown, risk per trade, position size, trades a day, trading
  hours, a news blackout, a cool-off after losses), kept in `trading-rules.json` in the app's
  config folder (rules and equity figures, no key material) and checked by
  the router's `place_order`, `amend_order` and `set_position_protection`
  before anything is signed. It only ever refuses, with `VenueError::Blocked` and a rule's
  code: an order that reduces a position, a cancel and a stop moved closer
  always pass. It reads the venue's own account, fills and closed trades, and
  fails closed (an opening order is refused when they can't be read). The
  news blackout (no new positions N minutes either side of a high-impact USD
  release) reads the economic calendar through `econ_calendar.rs`'s cached
  copy: it fails closed only while the calendar has never been read.
  Each account has its own set (a prop firm's, a venue's), checked only
  against that account's orders. Loosening a rule or turning a set off waits
  for the next 00:00 UTC; tightening applies at once. Deleting a set is
  the one way out that doesn't wait: it is immediate, on or off, behind a
  confirmation on the page. It guards a
  trader against themselves in this app, not against the page, and not
  against an order placed on the venue's own site (which still counts).
- `apps/desktop/src-tauri/src/share.rs` - the P&L share card. Saving
  writes the page's PNG (checked) to Downloads under a name Rust picks.
  `open_share` opens a social site's post page: the page names one of a
  fixed set of sites and passes a caption, and Rust builds the URL itself,
  the caption percent-encoded into its one query value - never a URL from
  the UI. The image goes by the clipboard, not through any site link.
- `apps/desktop/src-tauri/src/float.rs` and `apps/desktop/src/float/` - the
  floating window: a second window (the same frontend at `#float`) that stays
  over other apps and can reach the trading commands above. It adds none: its
  own commands only show, hide, move and size it, and it holds no key. Its
  order buttons need a 0.4s hold, and it is hidden from screen sharing by
  default. Giving it anything the main window can't do is a security-relevant
  change.
- `apps/desktop/src-tauri/src/chart_window.rs` and `apps/desktop/src/chart/`
  - a chart popped out of the Multi-chart page into a window of its own (the
  same frontend at `#chart?...`, up to 8). Rust builds the address: the venue
  and interval are the domain's types, the market id is checked first. Its
  one command opens a window; the page draws a chart only, with no order
  buttons and no key. Giving it any is a security-relevant change.
- The Multi-chart page's trading (`components/pages/MultiChartPage.tsx`):
  with "Trade" on, each chart on the venue on screen gets market buy and sell
  buttons that need a 0.4s hold, and a position's TP / SL lines can be
  dragged. Neither adds a command: they go through the same `placeOrder` and
  `protect` as the ticket and the Trade chart, so the same accounts can trade.
- Paper trading (`lib/paper.ts`, `lib/paperStore.ts`, `hooks/usePaper.ts`,
  `components/paper/`): on Hyperliquid and Aster (the venues without a demo)
  the header's Live / Paper switch picks where the Trade page's orders go.
  In paper mode every order path in `App.tsx` (`placeOrder`, `cancelOrder`,
  `amend`, `protect`, leverage and margin mode) changes a simulated account
  kept in this machine's storage, and the venue's own account isn't read;
  nothing is signed or sent, and the paper code imports no venue client. A
  live call checks again that its venue hasn't gone to paper since the
  render, and the floating window (which calls the venue itself) places no
  order while its venue is in paper mode. Paper results never reach the
  menu bar, and a paper share card says "Paper". Routing a paper order to a
  venue, or a live one to the paper account, is a security-relevant change.
- Onboarding stores a venue's trade-only delegated key (Hyperliquid agent
  wallet, Aster API wallet with withdraw off), not the
  user's main wallet key.

The webview CSP in `apps/desktop/src-tauri/tauri.conf.json` is part of this
surface, not cosmetic. `connect-src` allows `'self'`, IPC, and WalletConnect's
relay and verify hosts (`wss://relay.walletconnect.org`,
`https://verify.walletconnect.org`), which onboarding needs to reach the
user's wallet - nothing else, and never a venue: venue crates make every venue
request. No key passes through the webview for WalletConnect either: Rust
generates the agent key and builds the approval, and only the wallet's
signature comes back (`wallet.rs`). Each venue crate connects only to its own
hosts and explicitly configured RPC endpoints.

## Live trading

Orders work on Bybit (demo accounts, and live accounts with live trading
turned on in the account's details - the API key dialog), and on Hyperliquid
and Aster once live trading is turned on for the connected wallet (the
Connect wallet dialog; there is no demo there, so every account is live).
`components/wallet/LiveTradingSwitch.tsx` is the switch in both dialogs, and
`lib/liveTrading.ts` mirrors Rust's list for the page. A trading live
account shows a "Live" badge on the ticket. Everything works on all three
but a trailing stop on Hyperliquid and Aster, which answers "not supported
by this venue"; there, only a resting limit order's price and size can be
changed.

## Paper trading

Hyperliquid and Aster have no demo, so they get paper trading instead (Bybit
has its Demo Trading accounts). The Live / Paper switch beside the venue
chips is per venue; in paper mode a slim banner over the workspace shows
the paper P&L and the way back to live, and the ticket says "Paper". The
account itself is the Paper panel (`paper`; `components/panels/PaperPanel.tsx`,
`lib/paperOverview.ts`), put in the layout the first time paper mode is
turned on (and from the banner or the palette after): equity and P&L, open
P&L, margin, fees and funding, the realized P&L curve, how the trades went,
and a journal of fills, closes and funding, with Funds (add up to 100,000 at
a time, or take out what isn't held as margin; neither counts as P&L) and
Reset (behind a confirmation: every position, order and record gone, back
to 10,000; `components/paper/PaperFundsDialog.tsx`). It reads the paper
state only and places nothing. It
keeps everything in this machine's storage (`pd.paper.<venue>`), so it
survives a restart. It needs
no wallet. Orders fill on the venue's live prices (the book's best bid and
ask for the market on screen, the mark from the summaries for the rest) at
the venue's own fees: market (within its slippage bound), limit (GTC, IOC,
post-only; resting ones fill as a maker once the price reaches them),
trigger, attached and position TP / SL, trailing stops, reduce-only,
leverage and margin mode, funding at each interval, and liquidation at an
estimated price. It moves forward once a second while the app runs, for the
venue on screen only. Trading rules aren't checked on paper orders.

## Trading rules

The Trading rules page (`components/rules/`, after the Rules mockups in
`design/`) edits each account's rules (one set per account, picked at the
top of "Your rules") and shows where the chosen account stands: Rust keeps
both (`crates/engine/src/rules.rs`; `lib/tradingRules.ts` mirrors its `Rules` and
`Status`), and `hooks/useTradingRules.ts` reads them on a timer, raises the
notifications (a limit close, a lock, a cool-off, a revenge trade) and feeds
the banner above the workspace. Rules are checked on any venue's orders,
from that venue's fills and closed trades (Hyperliquid's and Aster's are
built from their fills); if they can't be read, an opening order is refused
(they fail closed). The news blackout reads the economic calendar
(high-impact USD releases only, `NEWS_CURRENCIES`), and the dashboard shows
the next one. The order ticket asks `check_trading_rules` as an order is
filled in (`checkRules` on `OrderTicket`, for a live or demo account with
rules on, never a paper one) and shows what would refuse it, or only warn,
before it's sent; Rust's own check in `place_order` still decides.

## PewterDesk AI

A page (`ai`; `components/pages/AiPage.tsx`, `hooks/useAiChats.ts`,
`lib/aiChats.ts`), after CoinMarketCap's CMC AI: a chat with a market

and announcements, the economic calendar and the web, recent trades and

in `ai-chats.json` (not the webview's storage, which the market caches

Settings › Layout shows every preset and saved layout as a card

## The daemon and `pd` ("always on")

Phase 3 of the plan, built: `pdd` keeps the engine (and its algos) running
with the app quit; `pd` trades through it from a terminal, reading the
command palette's own lines (`pd buy 100 hype at 38.2`, `pd chase ...`,
`pd halt`, `pd flatten`), each previewed and confirmed (`--yes`,
`--dry-run`, `--json`); without `pdd` it reads markets and prices on its
own and refuses to trade. `pd daemon install` (macOS) copies `pdd` into
the app's data folder and runs it as a LaunchAgent (`KeepAlive`); `pd pair`
pairs a `pd` once; `pd use <venue> <account>` picks the account. In the
app, Settings > Advanced > Always on does the same for the app. Development:
`PEWTERDESK_HOME` puts the daemon's and `pd`'s files in one folder of its
own.

## Algos and `pd`

Phases 0 to 3 of `docs/bots/plan.md` are built: `crates/engine` does the
routing and the trading gate (the router, `live.rs` and `rules.rs`, the
event log in `crates/store`, client order ids), runs the algo executors
(chaser, TWAP, scaled, in `crates/engine/src/algo/`, tested against
`SimVenue` in `crates/sim`; Hyperliquid's own TWAP, the venues' dead-man's
switches and `expiresAfter`), inside the app or headless in `pdd`, which
`pd` and the app reach over a localhost-only protocol. The decision is
`docs/adr/0003-bot-engine-daemon.md`.

No bot engine runs in pewterdesk yet. Automated strategies run in
FreqTrade, on its own, with its own trade-only key (ideally its own
sub-account): it doesn't talk to pewterdesk and pewterdesk doesn't talk to
it. Its trades show here like any made elsewhere, and count toward that
account's trading rules. The bot engine that was built here (strategies, a
backtester, paper and live bots, `pd bot`) is kept on the `bots-engine`
branch, unmerged. The bots' UI is on main without it (below).

When working on the engine, the daemon or `pd`:

- `docs/bots/safety.md` is binding: no new signing verbs (the six operations
  above only), every order through the one gate whatever sent it, keys only
  via `KeySource`, localhost and paired clients only, fail closed.
- Keep `docs/bots/` and the ADR in step with the code; if the plan changes,
  change the doc in the same PR.

## Bots panel and page

The UI for bots, with no engine behind it: a panel kind (`bots`;
`components/panels/BotsPanel.tsx`) and a page (`bots`, last in the menu so
it takes Cmd+9; `components/pages/BotsPage.tsx`), sharing
`components/bots/parts.tsx`, `hooks/useBots.ts` (one instance in
`App.tsx`, which raises their notifications) and `lib/bots.ts` (the types
and the arithmetic, no React). The panel shows the bots on the market on
screen (running, paused, stopped; pause, stop, halt all), a form to start
one from a saved backtest as a dry run on the backtest account or live (a
live bot needs the account's live trading on, as the ticket does), and
their log. The page compares each bot with the backtest it came from:
its curve against the backtest's over the same bars, daily P&L, trades,
events, P&L by hour, and whether it's in line after 10 closed trades.

halted, the engine out of reach, history unreadable.
They read a `BotSource` (`lib/botSource.ts`); the app's is `noEngine`,
which shows nothing and refuses every action. `lib/botDemo.ts` is a demo
source for development builds only (`import.meta.env.DEV`; "Show demo
bots" in the empty state, with a state picker): its bots are marked
`demo` and say so, and it sends nothing. Wiring a real source - Tauri
commands that start, pause or stop a bot - is a security-relevant change:
every order a bot sends must go through the router, as the algos' do.

## Notifications

Anything worth telling the user (an order, a fill, a position change, a fired
alert, a liquidation warning) goes through `notifyEvent` in
`apps/desktop/src/lib/notifications.ts`, not a bare `toast()`. It records the
event in the notification centre and delivers it where Settings >
Notifications says (toast, desktop, sound; do not disturb holds back all but
liquidation risk). An alert set to show in the menu bar takes the tray
item's title for 20 seconds (`lib/trayFlash.ts`). Market alerts live in `packages/ui/src/lib/alerts.ts` and
`hooks/useAlerts.ts`; they are checked in the app while it runs - there is no
backend, so nothing fires once the app is quit.

## Interface strings

Every user-facing string goes through `t("key")` from `@pewterdesk/ui`; don't
hardcode text in components. English in `packages/ui/src/i18n/locales/en.ts` is
the source of truth, and the other seven locales are typed against it, so a
new key fails the typecheck until every language has it. The language is fixed
per session (switching reloads the app behind the splash), so never call `t` at
module scope - it would run before the locale loads. Numbers stay en-US in
every language on purpose; dates follow the locale via `dateFormat`.
